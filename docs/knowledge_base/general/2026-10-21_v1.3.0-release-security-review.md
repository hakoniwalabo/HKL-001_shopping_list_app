## 2. 追加確認事項

### 並び替えのインデックス補正

`list_reorder_bar.dart:28` は `onReorder` ではなく `onReorderItem` を使っています。`onReorderItem` は「取り除いた後の挿入位置」を返すため、`newIndex -= 1` の補正は不要です。既存の商品並び替え（`item_provider.dart:65-69` のコメントと実装）・よく買うもの並び替え（`favorites_screen.dart:223`）と同じ前提で、`_onReorderList` の `removeAt`→`insert`（`shopping_list_screen.dart:456-458`）と整合しています。範囲外インデックスで例外になる経路は見当たりません。

### 並び替えモード中のタブ同期

並び替えモードの間は `TabController` の順序を作り直さず、モード終了時に `currentListId` の新しい位置へ `animateTo` で同期しています（`shopping_list_screen.dart:449-453`）。表示中のリストIDは並び替えで変わらないため、別リストの商品へ誤って書き込むような経路はありません。

### ヘルプ更新

Rules.md「機能を追加・変更・削除したときは `help_dialog.dart` を同時に更新」について、`help_dialog.dart` に「リストの並び替え」項目の追加と「商品名の候補表示」説明の更新が含まれていることを確認しました（セキュリティ観点外ですが、リリース条件として記録します）。

## 4. 参考（推測・確信度8未満、修正必須ではありません）

**参考1：インポートされた「よく買うもの」の価格が未正規化のまま候補に流れる（確信度3/10、既存挙動）**
`importData` の favorites 取り込み（`database_helper.dart:759-781`）は個数を `>= 1` に正規化していますが、価格はバックアップの値をそのまま挿入しています。改ざんされたバックアップで価格が負数になっていた場合、今回の候補選択で `_priceCtrl` に負数が入ります（`add_item_dialog.dart:93`）。ただし保存時に `price_field.dart:20-28` の validator で弾かれるため、不正値がアイテムとして保存されることはありません。価格が文字列などの非数値だった場合は `favorite_suggestion.dart:19` のキャストで例外になり候補が表示されなくなりますが、同じデータは既存の `favorites_screen.dart:152, 163` の `as int` でも同様に失敗するため、今回の差分で新たに生じたリスクではありません。攻撃者はバックアップファイルを自分で用意したユーザー本人に限られ、外部から悪用できる経路は無いと判断しています。改善するなら、インポート時に個数と同様に価格も `>= 0` の整数へ正規化する方法が考えられます。

**参考2：`_loadFavorites` に例外処理が無い（確信度2/10）**
`add_item_dialog.dart:78-84` は `getFavorites()` の失敗を catch していません。失敗時は Future の未処理例外としてログに出るだけで、ダイアログ自体は候補なしのまま動作を続けます。データ損失やユーザー向け情報露出は無く、可用性上の影響も軽微です。

**参考3：並び替えを短時間に連続実行した場合の書き込み順序（確信度2/10）**
`_onReorderList` は await 完了を待たずに次のドラッグを受け付けます。sqflite はトランザクションを直列に実行し、各呼び出しはその時点の画面状態全体を書き込むため、最後の操作の順序がDBに残る想定です。理論上の競合はありますが、仮に順序がずれても `sortOrder` の値が変わるだけで、データ損失は発生しません。

**参考4：マイグレーションの `catch (_)` が列重複以外の失敗も吸収する（確信度2/10）**
`database_helper.dart:196-202` は ALTER の失敗理由を区別していません。ただし、列追加が本当に失敗していれば直後の `batch.update`（`:208-216`）が存在しない列への更新として例外になり、トランザクション全体がロールバックされます。そのため不整合な状態で v9 として確定することはありません。v6〜v8 の既存マイグレーションと同じパターンです。
